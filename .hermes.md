# Hermes project rules — jev-roster-shapes

Hermes: when working in this repo, adopt this behavior. `AGENTS.md` (repo
root) is the operating manual — commands, layout, invariants, boundaries.
This file adds Hermes-specific conduct; do not duplicate it, layer on it.

## Session behavior

- Read `SPEC.md` plus this milestone's entry in `ROADMAP.md` before your
  first code edit in a session. `docs/DOMAIN_AND_CALCULATIONS.md`,
  `docs/DATA_CONTRACT.md`, `docs/WORKFLOWS.md`, `docs/ACCEPTANCE.md`, and
  `docs/DECISIONS.md` each gate the corresponding kind of change — see
  AGENTS.md §Read before changing a component.
- Document any deliberate contract revision in the same change as its
  implementation, and record material design choices in
  `docs/DECISIONS.md` before building against them.
- Run `git diff --check` before declaring documentation edits done.
- Synthetic fixtures stay visibly labeled and separate from any permitted
  team data. External model processing and deployment are separate
  decisions that require their own user go-ahead — local prototype work
  continues unaffected while those are unresolved.
- Commits: Conventional Commits (`type(scope): subject`). The machine-wide
  commit-msg hook (`core.hooksPath=~/.config/git/hooks`) enforces this in
  every repo, including the first commit of a brand-new repo. If a commit
  is rejected for format, retry as `chore: <subject>`.

## Skill routing (Hermes skills — load with skill_view before the task)

Run Hermes for this repo via the repo-root **`./dev`** script. It is
idempotent: it creates the **jev-roster-shapes profile**, prunes
irrelevant skills from that profile via `skills.disabled`, bootstraps the
repo-local project skills in `.hermes/skills/`, and ensures the repo is
trusted — then drops you into a session. Subcommands: `./dev setup`
(bootstrap only), `./dev doctor` (verify environment), `./dev -z "prompt"`
(one-shot; all other args pass through to hermes). The default profile
keeps the full catalog for everything else.

| Task in this repo | Load skill |
|---|---|
| Writing any new feature or fix | `test-driven-development` — tests first; pure logic in small modules with `*.test.ts` beside them |
| A bug that isn't immediately obvious | `systematic-debugging` — root-cause before fixing |
| Before committing code changes | `requesting-code-review` — static scan → gates → independent reviewer → fix loop. Mandatory for multi-file changes |
| Executing an approved plan (multi-task) | `subagent-driven-development` — fresh implementer subagent per task, two-stage review |
| Plan interview before implementation | `grill-me` — invoked by the user, but expect it even after "go" |
| Calling TypeSafe Jev via the local `jev` CLI | `jev-tooling` |
| Messy milestone chunk just landed | `simplify-code` — run after each milestone, not mid-milestone |
| Validating an unknown design before building | `spike` — throwaway experiment first; findings go in `spikes/`, never half-landed code |
| "How big is the codebase" metrics | `codebase-inspection` |
| PRs, issues, reviews on the GitHub repo | `github` |
| Substantial autonomous/multi-step work | `unlazy` — keep working to verified done, no stubs |
| Hermes config/theming questions | `hermes-agent` |

Negative controls — do NOT load a skill for a near-neighbor ask:

- A one-off question about the `jev` CLI ≠ `jev-tooling` (that is the
  call procedure); answer directly.
- An ordinary reproducible bug ≠ `spike`; spike is for validating an
  unknown *design* before building, not debugging.
- A failing test in existing code ≠ `test-driven-development` from
  scratch; reproduce, then `systematic-debugging`.
- Idle "how big are we" ≠ a full `codebase-inspection` run unless metrics
  were actually requested.
- Doc/comment wording tweaks load no skill at all.
- React-ecosystem skills (`pick-ui-library`, `emil-design-eng`,
  `ask-sonner`) do not fit this repo — it is Svelte/SvelteKit.

## Hooks (jev-roster-shapes profile)

Configured in `~/.hermes/profiles/jev-roster-shapes/config.yaml`, scripts
in `~/.hermes/agent-hooks/`:

- `jev-roster-shapes-git-guard.sh` — pre_tool_call on
  `terminal|execute_code`, fail_closed: blocks mutating git
  (push/pull/commit/merge/...); read-only git passes. Commit through the
  user or with explicit approval.
- `jev-roster-shapes-formatter.sh` — post_tool_call on `write_file|patch`:
  runs prettier on edited TS/JS/JSON via the repo's `node_modules/.bin`
  (prettier is present here, so it actively formats).
- `jev-roster-shapes-evidence.sh` — post_tool_call on `terminal`: appends
  a compact JSONL line per command to
  `~/.hermes/agent-hooks/jev-roster-shapes-evidence.jsonl`.
- `jev-roster-shapes-inject-git-status.sh` — pre_llm_call: injects branch
  + dirty-file status when the session cwd is inside this repo (matched
  on the `jev-roster-shapes` origin fragment).

First session start may prompt for per-profile hook allowlist consent, or
run `hermes --profile jev-roster-shapes --accept-hooks` once.

## Engineering gates (do these yourself, unprompted)

- `bun run check` (svelte-check, --fail-on-warnings) and `bun run test`
  (vitest) must be green before declaring any code change done; run the
  full `bun run verify` before closing a milestone chunk.
- Keep quantitative results invariant under layout and presentation
  changes (AGENTS.md §Implementation boundaries) — the test suite plus
  `docs/ACCEPTANCE.md` checks are the evidence, not eyeballing.
- Preserve replay inputs and calculation version: a saved result must be
  reproducible without a future provider response.
